# D4 Claim Support Skill

skill_id: claim_support_skill
stage: D4_claim_support

## Mission

Collect evidence about whether the output observed in D3 can be connected to the paper's claims, method workflow, experiments, tables, figures, case studies, or result objects. Then apply the rubric's Functional predicate as a D5 entry gate.

D4 is a claim/result support stage. It is not an execution stage and does not assign final D1-D5 scores, Reusable status, or a badge. It reads the paper and prior stage evidence, explains the mapping between observed output and paper targets, records coverage and conflicts, and writes a reviewer-readable stage packet. Unlike earlier evidence stages, D4 must also make a strict rubric-grounded Functional decision so the runtime can decide whether D5 reuse validation is meaningful. Final scoring later rechecks this predicate together with all other badge fields.

## Tools

Use only the general tools needed for reading and recording evidence:

- `read_file`
- `get_paper_info`
- `write_file`
- `phase_finish`

Do not use `run_command` in D4. D4 does not run new workflow commands, rerun experiments, repair the artifact, or create new execution evidence.

## Core Rules

1. D4 collects claim-support evidence and applies only the Functional predicate.
   Use the stage mission to organize evidence around observed outputs, paper targets, mapping strength, coverage boundaries, and conflicts. Do not assign final `R`, `WR`, `WA`, `A` dimension scores, Reusable status, or a badge conclusion in D4. D4 must decide whether the rubric Functional predicate currently holds, because D5 requires Functional as a prerequisite. This is an evidence gate and must be written as `functional_predicate`, not as a final badge recommendation.

   Functional holds only if all rubric conditions hold:
   - Available holds from `artifacts/available_gate/stage_packet.json`;
   - D2 evidence is at least WA-level: documented/prepared executable environment with acceptable intervention boundary;
   - D3 evidence is at least WA-level: a representative workflow reaches a checkable state and produces valid output;
   - D4 evidence is at least WA-level: reviewer-observed D3 output maps to at least one locatable paper target with support or limited support;
   - at least one representative workflow satisfies RW1-RW5;
   - evidence tier is E2 or E3, not E0/E1;
   - the successful path does not depend on I4;
   - if the highest intervention is I3, the semantic-preserving rationale is recorded.

   Do not guess missing conditions. If a condition is not supported by concrete stage evidence, mark it unsatisfied or unknown and set `functional_predicate.holds=false`.

2. D4 depends on D3 reviewer-observed execution evidence.
   The primary and required D4 evidence is `artifacts/D3_executability/stage_packet.json`, `artifacts/D3_executability/route_evidence.json`, `artifacts/D3_executability/evidence_semantics.json`, and the command/output refs listed there. D4 claim support requires D3 to have produced `E2` or `E3` reviewer-observed output. If D3 did not produce valid reviewer-observed output, record why D4 claim support cannot be established. Repository files, author-provided notebooks, precomputed result files, static tables, cached models, or README claims may be described only as auxiliary context; they must not be treated as D4 claim-support evidence by themselves.
   Preserve D3's distinction between confirmed facts and suspected causes. Do not upgrade a suspected GPU/API/resource explanation into a confirmed D4 limitation unless the D3 packet or cited logs directly support it. If D3 records an environment-context propagation issue, missing module, wrong interpreter, or unresolved execution-context question, carry that exact diagnosis forward.

3. Paper targets must be locatable.
   A paper target should have a paper text location or a clear paper section/phrase/table/figure/result object. Prefer targets from the abstract, introduction, evaluation section, result tables/figures, case studies, and explicitly named claims.

4. Output interpretation must be evidence-grounded.
   Explain reviewer-observed D3 output using README, paper text, D3 logs, generated files, notebook output generated by the reviewer, result files generated or validated by the D3 workflow, or reviewer notes already recorded in prior stages. Do not infer claim support from README promises, repository files, or author-provided precomputed outputs alone. For API/resource-gated or expensive artifacts, distinguish "precomputed files merely observed" from "deposited result-package contents loaded, extracted, checked, aggregated, or summarized by the reviewer in the current run"; the latter may support claim mapping when it is artifact-specific, paper-facing, and has a clear coverage boundary.

5. Map only what the evidence supports.
   If D3 produced a reduced/demo/example output, map it to the method step, result type, artifact goal, or evaluation target it actually covers. Do not present a reduced run as full paper reproduction.
   If D3 records `generic_dependency_or_example=true`, `component_only=true`, `artifact_specific_logic_exercised=no`, or `paper_facing_output=no`, D4 must record that evidence boundary unless the packet can cite concrete evidence that the observed output exercises the artifact's paper-facing logic. Do not map a third-party dependency example, generic tool demo, build test, or helper utility output directly to a paper claim merely because the dependency is used somewhere in the artifact.

   For multi-component systems, distinguish component-level evidence from system-level claim support. If the D3 route exercised only an offline component, generic library example, packaged dependency, or minimal probe while an online/client/service/integration component required by the paper is missing or unevaluated, record a `component_only` coverage boundary. The mapping may support a component claim, but it cannot by itself establish support for the whole paper-facing system claim.

6. Support judgment is descriptive, but Functional gate is explicit.
   For each mapped target, state whether the available output appears to support, provide limited support for, not support, or cannot evaluate that target, and explain why. This is evidence for final scoring, not the final score itself.

   In `functional_predicate`, convert the mapped evidence into the rubric Functional boolean. In `handoff`, restate the Functional predicate and evidence facts without assigning a final badge or Reusable conclusion.

7. Record coverage boundaries.
   Always state what the D3 output covers and what it does not cover. If D3 is E0 or blocked, the boundary should clearly say that no executable output exists for paper mapping.

8. Record conflicts or differences.
   If observed output differs from paper/README claims, record the difference and plausible cause when evidence permits. If no conflict was observed, say that no conflict was observed within the limited evidence, not that the whole paper is verified.

9. Static or precomputed evidence is auxiliary only.
   If D3 did not generate fresh reviewer-observed output but static/precomputed files exist, label them as auxiliary static/precomputed context and explain whether they are interpretable. Do not treat them as fresh execution, and do not use them to establish D4.1.

   Dataset/result package rule:
   If D3 executed a representative bounded extraction/loading/aggregation workflow over documented data/result files and produced reviewer-observed summaries, those generated summaries may be mapped to paper tables, figures, research questions, or numerical claims when possible. The D4 evidence is the D3 reviewer-observed summary/output, not the mere existence of deposited files. If D3 only inspected or observed repository files without producing representative `E2/E3` output, D4 claim support remains blocked.

   Always record the coverage boundary: reviewer-side data/result recalculation is not the same as rerunning raw data collection, instrumentation, model training, or full experiments.

10. Avoid overclaiming external-state permanence.
    If a Docker image, dataset URL, API, service, or download failed during this run, describe it as "unavailable in this run" or "failed during current evaluation" unless the evidence proves a permanent removal. Do not call an external resource permanently unavailable from a single failed pull or request.

11. Do not ask author-clarification questions by default.
    Only record an author clarification need when claim support is blocked by a specific missing fact that cannot be resolved from the paper, README, artifact files, or D3 evidence.

## Workflow

1. Read prior evidence:
   - `artifacts/D1_documentation/stage_packet.json`
   - `artifacts/D1_documentation/readme_workflow.json`
   - `artifacts/D2_environment/stage_packet.json`
   - `artifacts/D3_executability/stage_packet.json`
   - `artifacts/D3_executability/route_evidence.json`
   - `artifacts/D3_executability/evidence_semantics.json`
   - `artifacts/memory/current_stage_memory.md`

2. Ensure full paper text is available.
   Read `artifacts/paper_source/paper_text.txt` if it exists. If it does not exist or is clearly incomplete, call `get_paper_info` without a page limit, then read the extracted paper text.

3. Read targeted D3 output refs when needed.
   Use `read_file` for logs, result snippets, generated-file listings, notebooks, or output summaries referenced by D3. Read only what is needed to explain the mapping; do not copy large outputs into the packet.
   When a D3 limitation affects claim support, read the relevant D3 log or output ref before summarizing the limitation. Do not rely only on D3 memory prose if the exact error name matters.

4. Identify paper targets relevant to D3.
   Choose a small set of targets that the D3 workflow output could plausibly support. Examples:
   - a paper method step implemented by the artifact;
   - an evaluation object or benchmark target;
   - a table, figure, metric, result object, or case study;
   - an author-declared full or reduced reproduction target;
   - a paper claim directly tied to the artifact's stated goal.

5. Compare D3 evidence to the selected paper targets.
   For each target, record:
   - paper location or quoted phrase fragment;
   - D3 evidence used;
   - what the output shows;
   - whether it supports, provides limited support for, does not support, or cannot evaluate the target;
   - coverage boundary and any conflict/difference.

6. If D3 has no valid reviewer-observed output, still write a useful D4 packet.
   Explain the missing prerequisite, cite D3 blockers/logs, list the paper targets that would have been relevant, and state that claim support cannot be established from current execution evidence. Do not assign a D4 score.
   Before using this blocked path for a dataset/result package, verify whether D3 produced reviewer-observed output from a documented bounded extraction/loading/aggregation/result-validation workflow. If D3 only observed static files or README claims, treat them as auxiliary context only. If D3 actually loaded, extracted, checked, aggregated, or summarized artifact-specific deposited results into a paper-facing validation output, map that output to paper targets and record the exact coverage boundary; do not automatically demote it to auxiliary solely because upstream generation was API/resource-gated.

7. Apply the Functional predicate.
   After claim mapping, write `functional_predicate` using the rubric conditions above. This decision controls whether D5 should run:
   - if `functional_predicate.holds=true`, set `d5_next_action` to `proceed_to_D5`;
   - if `functional_predicate.holds=false`, set `d5_next_action` to `skip_D5_go_to_final_scoring`;
   - if the evidence is incomplete or internally contradictory, set `holds=false` and explain the exact missing or conflicting condition.

   D4 may say "Functional predicate holds" or "Functional predicate does not hold" because this is the explicit gate required before D5. Do not recommend a final badge.

8. Write `artifacts/D4_claim_support/stage_packet.json` in natural language.
   Include:
   - `stage`
   - `stage_goal`
   - `status`
   - `summary`
   - `paper_sources_used`
   - `d3_evidence_used`
   - `paper_targets_considered`
   - `selected_mapping_targets`
   - `claim_support_mapping`
   - `d4_evidence_profile`
   - `representativeness_for_claims`
   - `functional_predicate`
   - `d5_entry_gate`
   - `coverage_boundary`
   - `conflicts_or_differences`
   - `unsupported_or_unchecked_claims`
   - `limitations`
   - `author_clarification_needs`
   - `handoff`
   - `evidence_refs`
   The `handoff` must transfer to D5 and final scoring the exact D3 output status, paper-target mapping, support/limited-support/not-support/cannot-evaluate judgments, coverage boundary, confirmed versus suspected blockers, and Functional predicate result. Do not include Reusable or final badge advice.
   The `representativeness_for_claims` object must explicitly carry D3's `artifact_specific_logic_exercised`, `paper_facing_output`, `generic_dependency_or_example`, `component_only`, and `representativeness_boundary` values, then state which paper claims or component claims the observed output can be mapped to. For resource/API-gated result packages, do not set `can_support_artifact_level_paper_claims=false` merely because fresh upstream generation was not performed; describe whether the current-run validation output is artifact-specific, paper-facing, checkable, and mapped to a locatable paper target.

   - append a concise D4 summary to `artifacts/memory/stage_summaries.md`;

   If `functional_predicate.holds=true`, replace `current_stage_memory.md` with a D5 starting note that states D3 output status, D4 mapping status, key refs, coverage limits, and the Functional predicate evidence that allows D5 to proceed.    This starting note must not assign Reusable status or any final badge.

10. In the same response as the final writes, call `phase_finish` when there were no write errors.

## Completion

Finish D4 when paper text and D3 evidence have been compared at a reviewer-usable level.

D4 may finish with:

- a clear mapping from D3 output to one or more paper targets;
- a limited-scope mapping with explicit coverage boundaries;
- a conflict/difference record between observed output and paper/README claims;
- a clear explanation that no claim support can be established because D3 produced no valid output or only static/precomputed evidence.
- a rubric-grounded `functional_predicate` that either allows D5 to proceed or instructs the runtime to skip D5.

Do not finish by assigning a final D4 score, Reusable status, or badge recommendation.
